# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Briefcase is a research project for font search via neural embeddings. Pipeline:
1. **Pretrain** a UNet or ViT to reconstruct uppercase glyphs from lowercase (or masked-glyph reconstruction), forcing the backbone to learn font style rather than letterform. Trained on font bitmaps rendered from thousands of `.ttf`/`.otf` files.
2. **Retrieval head**: freeze the pretrained ViT backbone, train a small head to predict style tags/adjectives (`retrieval.py`).
3. **Finetune**: train paired image/text embedders (ViT image side + CLIP or BERT text side) contrastively so a text query and a font's glyph images land in the same embedding space (`finetune.ipynb`, `finetuneViT.ipynb`).
4. **Search**: use the finetuned embedders to rank a font corpus against a free-text query, or against tag vocab (`utils/search.py`, exposed via `site/`).

There is also an exploratory line of work (`meander.py`, `trainMeander.py`, `testMeander.py`, `cluster_search.py`) on interactive/preference-based search — narrowing a font corpus through repeated pairwise or clustered choices instead of typing a query — plus transferability estimation (`estimation.py`) comparing pretraining objectives with LogME/TransRate/H-Alpha. See `README.md` for background, methodology and results tables.

## Architecture

### Config system (`utils/config.py`)

Everything is driven by `Config`, a dict-of-dicts wrapper loaded from JSON in `configs/*.json` (e.g. `configs/uppercase.json`, `configs/vit.json`, `configs/querying.json`). Supports dotted-key access (`config["model.layers"]`), attribute access (`config.model.layers`), and `"key" in config` membership checks — most model/dataset code branches on optional keys this way (e.g. `if "textProjection" not in config`) rather than using explicit defaults, so when adding a new model variant, prefer adding a new optional config key over changing call signatures.

### Models (`utils/unet.py`, `utils/vit.py`)

Both `UNet` and `ViT` are dual-purpose, switching behavior based on whether `config.model` has a `textProjection` key:
- **No `textProjection`** ("image" mode): used during pretraining. Outputs a reconstructed glyph image plus a character-classification logit (glyph identity is classified off the bottleneck/CLS features to force the backbone to separate style from letterform).
- **Has `textProjection`** ("pooled" mode): used during finetuning/embedding. Outputs a single pooled feature vector of that width, meant to be compared against a text embedding.

`ViTEmbedder` wraps a pretrained (frozen) `ViT` backbone with a trainable projection head for the finetuning stage — this is the actual "image side" of the contrastive image/text model. Both model classes have a `.load(path, name="checkpoint")` staticmethod expecting a directory with `<name>.pt` + `config.json`; checkpoints are organized under `checkpoints/{pretrain,retrieval,finetune}/<run-name>/`, with a `latest`/`best` symlink-equivalent kept per the `.gitignore` allowlist.

### Data loading (`utils/loaders/`, `utils/pretraining.py`, `utils/querying.py`)

`utils/loaders/` has one module per data source (`google.py`, `myfonts.py`, `dafont.py`, `standard.py`, `description.py`) — each knows how to enumerate a specific dataset's fonts/tags/descriptions on disk. `utils/pretraining.py` (`FontData`) builds lowercase/uppercase glyph pairs for the reconstruction pretraining task. `utils/querying.py` (`CombinedQueryData`) builds the paired image/text dataset for finetuning, and can pull from multiple `config.directories` sources at once (e.g. `myFonts` + `standard: [google, dafont]`, see `configs/vit.json`). Font descriptions are cleaned with spaCy (adjective/adjective-noun extraction).

### Search (`utils/search.py`)

`FontSearch` is the base class owning model loading, the font glyph dataset, cached per-font embeddings (persisted to `embeddings/<name>.json` via `utils/embeddings.py`), and top-k ranking; subclasses override `loadModels` / `embedFonts` / `encodeQuery`:
- `FontSearch` — CLIP-style image/text embedding search (the finetuned `ViTEmbedder` + `CLIPTextEmbedder`).
- `TagSearch` — searches via the multi-label tagging head from `retrieval.py`, mapping free text onto the tag vocabulary with spaCy.
- `ClusteringSearch` — narrows the corpus by iteratively assigning fonts to a k-ary cluster code (interactive digit-by-digit narrowing, no text query).
- `MeanderSearch` / `WalkSearch` — exploratory preference-walk search (positive/negative example steering, Bayesian-ish position updates); `WalkSearch` is used by `trainMeander.py`/`testMeander.py` to fit/evaluate a `PreferenceModel` over these walks.
- `GridFeedbackSearch` — "Interactive Grid-Feedback Retrieval": no text query, just repeated rounds of picking (or skipping) fonts from a grid, refit each round as an L2-logistic-regression belief over a whitened-PCA subspace of raw pre-projection backbone features. See **Ongoing investigation** below — under active evaluation, not yet wired into the site.

Local pygame UIs for trying these interactively: `search.py` (TagSearch/FontSearch), `meander.py` (MeanderSearch), `cluster_search.py` (ClusteringSearch), `draw.py` (draw a glyph, run it through a pretrained UNet), `hallucinate.py` (gradient-ascent glyph hallucination from a trained UNet classifier).

**Known footgun**: `FontSearch`'s `DEFAULT_BACKBONE` (`checkpoints/pretrain/latest`) has drifted out of sync with `DEFAULT_FINETUNE` (`checkpoints/finetune/2026-06-07 17-04/...`) — `latest` is now a 12-layer/embedDim-512 ViT, but that finetune checkpoint's image tower was trained against an 8-layer/embedDim-512 backbone (`checkpoints/pretrain/best` matches). Loading `FontSearch()` with default args throws a `state_dict` mismatch on `transformer.layers.8` onward; pass `backbone=os.path.join("checkpoints","pretrain","best")` explicitly until this is fixed.

### Site (`site/`)

`site/backend/app.py`: Flask + `sqlite-vec` for the deployed search API — stores per-font embedding vectors in a `vec0` virtual table (dimension = `config.model.textProjection`), plus font metadata, user accounts (JWT auth via `PyJWT`), and per-font text descriptions/registry data. `site/frontend`: Create React App (react-scripts 5), with route-like sections under `src/{search,map,about}`, each with its own `index.js` + `main.css`. `src/map` visualizes font embeddings spatially — `findCycle.py` generates the path data it walks (a greedy/evolutionary search for smooth tours through embedding space, used to pick which Google Fonts to feature on the front page).

## Ongoing investigation: grid-feedback search viability

**Goal, per the user:** implement `GridFeedbackSearch` (done, in `utils/search.py`), decide whether it's actually viable at the deployed corpus scale, and — once viable — replace the text/tag search in `site/` with it, removing the now-vestigial CLIP text-embedding code. **The site-integration/removal plan has not been started** — it's explicitly blocked on settling viability first.

### The algorithm, briefly

Offline: per-font raw backbone CLS features (pre-projection, pre-classifier — see `GridFeedbackSearch._rawFeatures`) → centre → PCA(D, D from the covariance participation ratio) → whiten → `Z`. Seed grid = k-means(Z, m) medoids. Online: each round, refit an L2-logistic regression from scratch on all labels collected so far (`GridFeedbackSearch._fitLogistic`), display the top-m unshown fonts by the fitted score. This matches a spec the user provided almost exactly (a simplified version of a fuller doc that also described Laplace-covariance UCB and a "Frontier" batch-diversification policy, dropped for the simplified version actually implemented).

### Evaluation harness

Not part of `utils/` — throwaway root-level scripts (gitignored is *not* set up for these, they're just untracked; not committed): `evalGridFeedback.py` (baseline top-m sweep + shared helpers other eval scripts import: `loadCorpus`, `fitProjection`, `seedGrid`), `evalGridFeedbackUCB.py` (fixed-κ Laplace-UCB), `evalGridFeedbackFrontier.py` (spec's geomspace-κ batch policy), `evalGridFeedbackUCBPE.py` (GP-UCB-PE), `evalTextNarrowing.py` (recall measurement for text pre-filtering, see below). All load `embeddings/all.json` directly (39,421 fonts, mean-of-per-glyph-normalized vectors, **not** raw CLS features — a deliberate simplification for fast iteration, not what `GridFeedbackSearch` itself uses) rather than recomputing embeddings, so they need no model/dataset load and run in seconds-to-minutes. **Correction:** `all.json` is *not* the `ViTEmbedder` contrastive-finetuning output as earlier notes here said — that's a separate file, `embeddings/allText.json`; `all.json` is on the raw/pretrain side, from the newer 12-layer pretrain checkpoint (see the diffusion investigation below for the effective-dimension numbers this affects). Simulated user: target font uniform at random, acceptance set `T` = its 10 nearest cosine neighbors (not just the exact font — matches the original design doc's `t=10`), each round's "true" positive labels are the k closest displayed fonts to the target by cosine similarity, each label flipped independently w.p. ε. Success = any of `T` appears in the displayed grid.

### Findings so far, in order

1. **Pure top-m works at the design doc's own tested scale, fails at deployed scale.** On a random 3,760-font subset (matching the doc's own corpus size), the harness reproduces its published numbers almost exactly (e.g. median 3 rounds at m=20,k=3,ε=0 — they report 3). On the full 39,421-font corpus, most `(m,k,ε)` cells **majority-censor** (>30 rounds) even at ε=0. Traced individual runs: the target's rank under the fitted weight genuinely wanders rather than trending down (0 → 6k → 13k → 136 → 1k → 3k → ...) — this is a real "absorbing basin" trap (top-m commits fully to one region every round; once wrong, nothing ever samples elsewhere again), not a scale/information-capacity wall. Demand at N=39,421 is only ~7.6 bits (`log2(N/(m·t))`, m=20,t=10) against ~14 bits/round supply (`log2(C(20,5))` at ε=0) — plenty of information-theoretic headroom that pure exploitation isn't using.
2. **Fixed-κ Laplace-UCB (`μ + κσ`, κ=1) roughly doubles the escape rate but is bimodal, not uniformly faster.** Censoring dropped from ~93% (κ=0, i.e. top-m) to ~58-63%. Critically: of the runs that *do* escape, they converge in median 4 rounds (mode exactly 3) — matching the small-corpus numbers almost exactly, confirming the trap-vs-demand diagnosis. The ~40-60% that don't escape within 30 rounds just don't, regardless of κ (swept 0.5-8, plateaus around 60-65% censored).
3. **The spec's own "Frontier" policy (`geomspace(κ_lo,κ_hi,m)`, one argmax pick per κ, dedupe, backfill) is *worse* than fixed κ, and has no literature grounding.** Searched specifically for the paper the fuller spec cited ("spherical-linear-BO") — not found. Diagnosed why it underperforms: the geomspace sweep is degenerate here (only 3-5 of 20 κ values produce distinct argmaxes; μ/σ don't reorder candidates continuously, only at a few "elbow" thresholds), so ~75-85% of every grid ends up filled by the backfill pass at κ_hi (near-pure exploration), diluting useful signal. Worse median (6-11 vs. fixed-κ's 4) and worse censoring (60-72% vs. 58-63%).
4. **GP-UCB-PE (Contal et al., ICML 2013 — real citation, implemented faithfully: one UCB-maximizing pick + m-1 pure-variance picks restricted to a "relevant region," posterior fantasy-updated after each pick) is a genuinely different, real tradeoff.** Escape rate roughly doubled again vs. fixed-κ (62-72% success vs. ~42%), but each escape is much slower (success median 10-20 vs. 4). Net overall median (censored included) still 17-24.5 — did not reach the "under 7" bar that was checked for. Prediction beforehand ("no" on <7) was right; the *reasoning* ("more exploration-heavy = lower escape rate like Frontier") was wrong — it actually escapes far more often, just slower per escape. Worth remembering: exploration-heavy ≠ automatically worse here, Frontier's failure was a construction bug (degenerate sweep + bad backfill weighting), not evidence against exploration generally.
5. **Net read on display-policy tweaks alone: probably a dead end for reaching small-corpus-like medians (~3-4) at full scale.** Three different policies (top-m, Frontier, GP-UCB-PE) all hit a similar wall. That convergence is itself a signal the bottleneck may not be the round-level display policy at all — see next finding.
6. **Metric mismatch is a real, separate, measured concern.** An oracle check (weight = target's own `Z`-vector, the best possible query) only gets 7/20 overlap with the true cosine-nearest-neighbors in the raw `V` space. The aggregator reasons in a whitened-PCA space built from `embeddings/all.json`; the simulated user's ground truth is cosine similarity in that same raw space — even a perfect fit only partially agrees with it. If this is the dominant bottleneck (not yet isolated from the trap problem), no amount of round-policy tuning fixes it; the offline PCA/whitening itself would need to target the right metric.
7. **Text-based pre-narrowing (user's idea: cut 39,421 → ~4,000 by text score before grid search) has real signal but a real risk at that exact cutoff.** Measured directly against the actual finetuned contrastive model (not a baseline) using each font's own real description as a proxy query (`evalTextNarrowing.py`, needs the `checkpoints/pretrain/best` backbone fix above to load): median target rank in the **top 2.2%** of the corpus (strong aggregate signal) despite R@1≈0% (confirms it's not viable as a direct prompt→font pipeline, consistent with why grid-feedback was built at all). At a hard 10%/~4,000-font cutoff: **18.3% of targets would be silently thrown away** before search even starts — too risky as an invisible hard filter for a real product. At 20%/~7,900: 7.3% loss, much safer, still ~5x corpus reduction. Recommendation: use text score as a **soft prior on round 1's seed grid** (bias k-means medoid selection), not a hard filter — captures the benefit without the silent-failure mode. Caveat: this measurement uses each font's *true* description as the query (idealized); a real free-typed user query is likely noisier, so real recall is probably somewhat worse than measured.

### Contrastive model improvement research (not yet tested empirically — analysis only, per explicit instruction not to script this part)

Read the actual training pipeline (`utils/training.py`'s `EmbeddingLoss`/`MoCoQueue`/`sigreg_weak_loss`, `utils/querying.py`'s `CLIPTextEmbedder`, `finetuneViT.ipynb`'s progressive-unfreezing schedule) before researching, to avoid recommending things already done.

- **Already implemented, don't re-suggest:** MoCo momentum queue (size 4096 in the config that actually trained the deployed checkpoint — `vit.json`'s 16384 is a red herring, doesn't match what's saved in the checkpoint's own `config.json`), InfoNCE with a sigreg anti-collapse regularizer (VICReg/Barlow-Twins-style, forces embedding covariance toward identity), a TF-IDF description-similarity **false-negative mask** (excludes accidentally-similar fonts from the negative pool — `buildFalseNegativeMask`), progressive block-unfreezing with a 10x lower backbone LR than head LR, and — important — **LLM-generated natural-language captions already exist** (`generate.py`, Phi-4-based, → `results/fontQueries.json`, 25,054/39,421 fonts × 8 diverse queries each; `CombinedQueryData` already prefers these over raw tag lists when present). Don't recommend "use richer captions," it's done for 2/3 of the corpus.
- **Real gap 1 — caption coverage:** only 25,054/39,421 fonts have the LLM-generated captions; the rest fall back to raw tag concatenation. Extending `generate.py` to the remaining third is cheap (proven pattern, just compute time) and probably the best ROI-per-effort item here.
- **Real gap 2 — CLIP itself is meaningfully outdated for this use case.** SigLIP (Zhai et al., ICCV 2023) replaced softmax-CLIP as the default open-source VLM pretraining objective by 2024. Relevant here specifically: SigLIP's sigmoid pairwise loss scores each image-text pair independently instead of forcing a single softmax "winner" per anchor, and trains well at much smaller batch/queue sizes than softmax-CLIP needs (this project's queue is 4096, far below CLIP-scale). Swapping the *loss*, not necessarily the text tower (queries here are short, so a heavier LLM-based text encoder like T5/LLM2CLIP is probably not worth the complexity) is the actionable version of this.
- **User's correction, important — naive hard-negative mining (e.g. FG-CLIP's approach, initially suggested) is likely a bad fit here and was walked back.** FG-CLIP-style hard-negative mining assumes a hard negative (embeds close, different label) is *wrong* — true for categorical vision-language data, false for font style, which is a graded/continuous similarity manifold where a "hard negative" is frequently a legitimate alternative answer (user's own framing: "the close fonts typically are also correct answers"). Forcing separation there would fight the real structure of the problem.
- **The actual right fix for that, found via literature, not first-principles guessing: Rank-N-Contrast (Zha et al., NeurIPS 2023).** Built for exactly this — continuous/graded target similarity — by contrasting samples on *relative ranking* in target space rather than binary pos/neg, so it never demands artificial separation between two legitimately-similar fonts, only correct relative ordering. The existing TF-IDF description-similarity matrix (currently only used to *exclude* false negatives) is already the right continuous signal to use as RNC's ranking target — no new data needed. SigLIP's independent-pairwise scoring and RNC's ranked-relative scoring are two different fixes for the *same* root cause (softmax forcing one winner per anchor); pursuing one or both together is more coherent than adding hard-negative mining on top of the current InfoNCE loss unchanged.
- **Untested, cheap, inference-time-only ideas worth trying before any retraining:**
  - **Prompt averaging** (ask for 2+ phrasings, embed each, average before scoring): grounded in multi-query/prompt-ensembling retrieval literature (GenQREnsemble; "why averaging embeddings works" in multi-query RAG). Matches the diagnosed failure signature precisely — R@1≈0% but median rank top 2.2% is the signature of high variance / low bias (roughly right neighborhood, wrong precise order due to single-phrasing word-choice noise), which query-averaging is the textbook fix for.
  - **"All-but-the-Top" (Mu & Viswanath):** mean-center, strip the top-k dominant principal directions, z-score the rest — a training-free postprocessing fix for anisotropic embeddings (a few directions dominate variance but carry mostly generic signal). This is the user's own "TF-IDF on portions of the vector space" intuition, confirmed as a real, named technique — z-scoring after removing dominant directions is the continuous analog of IDF-weighting (suppress generic/common directions, relatively boost discriminative low-variance ones). Would apply to the raw contrastive embedding space (`embeddings/all.json`), distinct from `GridFeedbackSearch`'s own whitening, which operates on a downstream PCA'd subspace built for the search algorithm specifically.

### Suggested next steps (not yet decided/started)

Isolate finding 6 (metric mismatch) from findings 1-5 (trap dynamics) before investing further in display-policy tuning — e.g. re-run the eval harness with the simulated user's "true" similarity computed in the *whitened Z-space* itself rather than raw cosine, to see how much of the residual censoring is metric-mismatch vs. trap. On the contrastive-model side, the two cheapest untested things (prompt-averaging, ABTT postprocessing) should be tried empirically before committing to any retraining path (caption-coverage extension, SigLIP/RNC loss swap), since both are inference-time-only against the already-trained checkpoint and would validate or kill those hypotheses cheaply.

## Ongoing investigation: text→visual-embedding diffusion (modality gap)

**Goal, per the user:** test whether a diffusion model can learn `P(visual font embedding | text embedding)`, as groundwork for evaluating the modality gap between visual and text embeddings. All code lives under `experiments/` (locally reorganized by the user into `experiments/diffusion-searches/`, matching the `choice-searches`/`text-searches` convention — the branch below still has it flat under `experiments/`). **This work is on branch `claude/laughing-noether-fodjhw`, not yet merged into `staging`** — check that branch out (or cherry-pick `experiments/`) before continuing it locally.

### Pipeline

```
experiments/embed_text_local.py         # -> embeddings/sentenceQueries_<model>.pkl {fontKey: [nQueries, dim]}
                                         #    run LOCALLY/GPU, not a CPU sandbox -- see Compute note
experiments/dataset.py                  # loading, matching, train/test split, PCAWhitener
experiments/diffusion.py                # DiffusionMLP, GaussianDiffusion (DDPM + step-respaced sampling)
experiments/train.py                    # -> checkpoints/diffusion/{checkpoint.pt, whitener.npz, config.json, test_pairs.json}
experiments/evaluate.py                 # recall@k over held-out queries
experiments/diagnose_conditioning.py    # generated-vs-true pairwise similarity structure
experiments/diagnose_text_ablation.py   # denoising loss, real vs. shuffled text, by noise level
experiments/diagnose_manifold_realism.py  # does generation look like ANY real font, right or wrong
experiments/embed_fonts.py, effective_dimension.py, character_variance.py, pooling_bug_check.py
                                         # side investigation into font_vit_embeddings.json, not the main path
experiments/branching.py                # interactive "decision point" search: ParticleBatch, advanceTo,
                                         #   findDecisionPoint, previewFonts, pruneAndResample -- see below
experiments/corpus.py                   # FontCorpus (nearest-font/ranking) + ClusterIndex (fixed corpus regions)
experiments/oracle.py                   # simulated user for branching.py, with an injectable error probability
experiments/evaluate_branching.py       # recall@k / decision-count sweep over oracle noiseProb
```

Visual target is `embeddings/all.json` (39,421 fonts — see the provenance correction above). Text is `results/fontQueriesV2.json` (18,940 fonts × up to 16 Gemma-generated queries), matched to `all.json`'s per-style-variant keys via the same longest-prefix-trie + shortest-name-per-family convention `experiments/text-searches/trainTextMLP.py` uses (`dataset.matchEmbeddingsToDescriptions`) — 17,056 fonts matched. Train/test holds out queries per font, not fonts (`dataset.splitQueryCache`, default 80/20) — the corpus is fixed, so the only real generalization question is unseen phrasing. Text encoder is swappable (`--model`/`--sentenceModel`, must match across `embed_text_local.py`/`train.py`/`evaluate.py`), defaulting to `BAAI/bge-large-en-v1.5` — a `[CLS]`-pooling model, unlike `trainTextMLP.py`'s mean-pooling `all-mpnet-base-v2`. **`embed_text_local.py` must run locally/GPU**: a full bge-large pass over ~380k queries measured ~3s/batch (batch 64) on a CPU sandbox, i.e. hours.

The diffusion model is a plain residual MLP (`DiffusionMLP`: sinusoidal timestep embedding + text embedding as conditioning, no visual info besides the noised target) trained as a standard DDPM (`--timesteps`, default 1000). `GaussianDiffusion.sample(..., numSteps=N)` supports sampling with fewer steps than training used via the OpenAI improved-diffusion "respacing" trick (evenly-spaced subset of training timesteps, effective β/α recomputed from consecutive selected steps' alphaBar ratio, model still queried at real training timestep values) — `evaluate.py --evalSteps` (default 50) uses this to match a faster production-realistic sampling budget without retraining.

### Effective dimension of the visual embedding spaces

`embeddings/font_vit_embeddings.json` (raw pretrained ViT CLS, mean-pooled over a-z, generated fresh this session from `checkpoints/pretrain/best`, ~39.5k fonts) has an effective rank (participation ratio, `effective_dimension.py`) of **~9.5 out of 512** — true even for individual, unpooled, per-letter embeddings before any pooling happens (`character_variance.py` rules out pooling as the cause; 89.5% of total per-letter variance is between-font, so it's not a letter-identity-vs-style confound either). `embeddings/all.json` has an effective rank of **~57.6 out of 512** — about 6x higher; **not yet explained** (the original hypothesis — contrastive finetuning — was wrong per the provenance correction above; likely just a better/larger pretrain checkpoint, unconfirmed).

Both files share a real, unfixed bug (`pooling_bug_check.py`): `utils/embeddings.generateEmbeddings` (`utils/embeddings.py:51`) L2-normalizes each of a font's 26 per-letter CLS embeddings, then mean-pools *without a final renormalize*. `mean_{i,j} cos(u_i, v_j) = ūbar · v̄bar` (plain dot product of centroids) but the stored embedding's cosine similarity divides by `|ūbar||v̄bar|` (both `<1`, and font-specific — they measure that font's own letter-to-letter consistency) — so cosine-similarity comparisons against these stored vectors systematically over/under-shoot the true average pairwise letter-cosine by an amount that varies per font. Measured: norms 0.70–1.00 (font_vit_embeddings.json) / 0.72–1.00 (all.json), only ~0.9% of fonts land exactly on the unit hypersphere. Concrete effect on 4 sampled fonts: cosine-of-means ran **0.01–0.05 higher** than the true mean-pairwise-cosine, every time, in the same direction. Fix would be normalizing *after* pooling (`normalize(embedding.mean(dim=0))`) — note "cosine of centroid" and "mean of pairwise letter-cosines" are different quantities regardless; fixing normalization order only gets you a valid version of the former.

### Diagnostic findings, in order

1. **First full-scale run** (17,056 fonts, 221,888 train / 51,164 test queries, bge-large, 60 epochs, loss 0.433→0.063, standard per-dimension standardization — no PCA yet): recall@k barely above random chance (recall@5 0.0004 vs. 0.000127 random at 39,421 candidates — ~2.4-3.3x chance across k, small in absolute terms).
2. **`diagnose_conditioning.py`** (generated-vs-true pairwise similarity structure, distinct-font queries): correlation ~0; generated samples averaged only ~0.13 cosine to the corpus-wide mean font vs. real fonts' ~0.75, with pairwise-similarity std ~0.68 (vs. ~0.044 expected for genuinely random 512-d vectors — the signature of a low-dimensional subspace unrelated to the real manifold). Identical at 50 vs. 1000 sampling steps, ruling out ancestral-respacing noise as the cause. **Caution for future work on this script and the two below: don't bake interpretive/"here's what this means" text into a script's printed output** — print numbers only; happened twice here and got called out both times.
3. **`diagnose_text_ablation.py`** (denoising loss, real vs. shuffled text, x0/noise/t held fixed, by timestep bucket): real beat shuffled at *every* noise level (~1-7% relative, peaking mid-schedule at 500-700) — rules out full conditioning collapse. Effect is real but modest.
4. **`diagnose_manifold_realism.py`** (nearest-neighbor cosine of generated samples against the full corpus, vs. real fonts' own leave-one-out nearest-neighbor baseline): real fonts sit in an extremely tight cluster (mean nearest-other-real cosine **0.96**); generated samples' best match anywhere in the corpus averaged only **0.40**. Most generated output didn't resemble *any* real font, right or wrong.
5. **Diagnosis: raw 512-d ambient diffusion forces the model to also predict noise across the ~450 near-degenerate dimensions `all.json` barely uses; small per-dimension errors summed over that many dimensions produce a large, essentially random perturbation dominating the real ~57.6-dim signal.** Fix: `dataset.PCAWhitener` (centre → PCA → whiten, fit on training fonts, `--pcaDim` default 64 — a little above the measured effective rank, "to allow for better differentiation" per the user) replaces plain per-dimension standardization. Same technique `GridFeedbackSearch` already uses for this exact anisotropic embedding space, applied here to the diffusion target instead of a search index. `evaluate.py`/`diagnose_*.py` all project generated samples back to the 512-d ambient space (`inverseTransform`) before computing cosine similarity, so results stay comparable across the change.
6. **Re-run after the PCA-whitening fix, same 17,056-font/bge-large setup:** realism **fixed** — generated-to-nearest-corpus cosine **0.9595** vs. the 0.9620 real-font baseline (was 0.40). Generated-to-own-target cosine **0.68** (was 0.10). Recall@k improved ~5-6x in random-chance-relative terms (recall@1 ~20x chance, was ~2.4x; recall@100 ~15x chance, was ~3.2x) but stayed low in absolute terms (recall@100 = 0.038). `fraction where nearest-in-corpus IS the true target` was **0.0000** even after the fix — realistic, reasonably-close-to-target generations still essentially never rank as the single closest match among 39,421 candidates, consistent with finding 7 in the grid-feedback investigation above (real fonts' own nearest-neighbor baseline is 0.96 — the corpus is dense enough with near-duplicates that R@1≈0% held even for the actual finetuned contrastive model via `evalTextNarrowing.py`). Read together: the generation-quality bug is resolved, conditioning does real (if modest) work, and the remaining shortfall looks like the same corpus-density ceiling other search approaches here already hit, not an obviously fixable new bug.

### Interactive branching search (decision points)

**Goal, per the user:** let a user narrow to a font with a text query plus a handful of clicks (capped at 5), redirectable mid-search, instead of typing one precise prompt (R@1≈0%) or a fixed multi-round protocol (`GridFeedbackSearch`). Design: run several reverse-diffusion trajectories from one text query as a batch of "particles" sharing one conditioning vector; when they're heading toward genuinely different parts of the corpus, pause, show ~10 representative fonts per direction, let the user pick, then continue with only that branch, repeating until fully denoised. Implementation: `experiments/branching.py` (portable primitives — `ParticleBatch`, `advanceTo`, `findDecisionPoint`, `previewFonts`, `pruneAndResample` — pure torch/numpy, no CLI/file I/O, meant to be driven identically by a simulated user now and a real one via a web endpoint later), `experiments/corpus.py` (`FontCorpus`, `HierarchicalClusterIndex`), `experiments/oracle.py` (simulated user with an injectable per-decision error probability), `experiments/evaluate_branching.py` (the eval harness). `diffusion.GaussianDiffusion.reverseSteps` was extended to also yield each step's free one-step x0 estimate (`x0Hat`, no extra model call) alongside `x`.

**An early version measured recall@10 ~5-10% and initial notes here concluded that was close to a hard ceiling set by the corpus/embedding space.** The user correctly pushed back on that: log2(39,421)≈15.3 bits is far less than the embedding space's own effective rank (~57.6, per the modality-gap section above), so a well-designed search protocol should be able to address the whole corpus in well under 5 rounds. That pushback was right — three real, fixable bugs in the search protocol were the actual cause, not the corpus or the model:

1. **Corpus density claim, checked directly, is a mix of a real metric bug and real (but not fatal) density — not "fundamentally indistinguishable."** Comparing four similarity metrics (ambient cosine, raw-dot-product corrected for the pooling-normalization bug above, whitened-space Euclidean, whitened-space cosine) against identical generated samples gave near-identical recall@k — the ranking metric wasn't hiding recoverable accuracy. But the ~0.96 nearest-neighbor cosine figure itself is partly a metric artifact: mean-centering drops it to ~0.92, and correcting for the pooling bug (comparing raw dot products of the un-renormalized pooled vectors — the quantity that actually equals true mean pairwise letter-cosine) drops it to ~0.85 and reorders the actual nearest neighbor in ~half of cases. Direct proof the corpus IS exploitable: an OMNISCIENT oracle (no diffusion model at all, just always stepping into the child that truly contains a known target) navigating a hierarchical k-means tree of the corpus (branching 10, depth 5) reached a median final group of **4 fonts** within 5 rounds across 200 targets — implied recall@10 ~97%.
2. **A flat, reused-every-round corpus partition (the original `ClusterIndex`, since replaced) caps addressable resolution at k regardless of round count.** Fix: `corpus.HierarchicalClusterIndex`, a real tree (10^5 = 100,000 addressable leaves, comfortably above the 39,421-font corpus), built once offline (~90s, cached via `--treeCache`).
3. **The decision logic only fired on a genuine ≥2-way tie and did nothing otherwise — including in the much more common case of one child clearly favored with no real competitor.** That left sessions stuck near the root (measured median final node size ~100, vs. the tree's own ~4-font omniscient ceiling). Fix: `assignToChildren` now returns a 3-way result (0 qualifying → keep advancing; exactly 1 → silently auto-descend, no ambiguity to ask about; ≥2 → ask). This alone brought median final node size to ~6-7.
4. **Auto-descending on model "confidence" doesn't track correctness.** Measured: the model's majority-vote top-level child choice matches the true target's actual child only 46.7% of the time (vs. 10% chance at branching factor 10) — real signal, but a "confidently wrong" model concentrates particles just as readily as a confidently right one, so a high `minClusterSize` bar let auto-descent (unsupervised) fire far more often than asking the oracle (reliable when consulted, since it scores against real acceptance-set similarity, not model belief). Fix: much lower `minClusterSize` (2, from an initial 8/40=20%) biases the system toward using its full `maxRounds` budget asking rather than trusting the model's raw top pick. `minClusterSize=1` was tried and found WORSE than 2-3: with nearly every child getting ≥1 particle, the qualifying set rarely stayed stable across `persistFor` consecutive checks, so sessions often gave up on descending at all.
5. **Recoverability from a wrong decision was tested, not assumed — and mostly didn't pay off.** A hard-pruned commit is irreversible by construction, a real risk the user flagged directly (large, high-stakes, necessarily-imperfect decisions shouldn't be unrecoverable). Two fixes tried: (a) a global L2-logistic belief (`belief.py`, matching `GridFeedbackSearch`'s own approach) refit each round from shown-vs-chosen fonts — measured ~0-1% recall@10 on its own, worse than doing nothing (too few, too geographically-narrow labels — a handful of rounds along one converging path — to fit a useful *global* linear ranking over 39,421×64, a genuinely different label regime than grid-feedback's many broadly-explored rounds); (b) pooling rejected-branch completions into the final ranking (`oracle.runSession`'s `reserveX`), which measured worse against the full corpus (the same dilution effect other search work here already knows about — more samples help distractors as readily as the true target) until restricted to branches actually considered AND capped by branch size (`hedgeMaxBranchSize` — an early rejected branch is itself huge, so hedging on it unconditionally reintroduces the same dilution one level down). Even fixed, `hedge` still trails `hard` up to noiseProb≈0.5 — but **overtakes it at noiseProb 0.7–1.0** (recall@100 0.19–0.21 vs. 0.16): exactly the regime the user's concern was about, where the decision-maker is unreliable enough that an irreversible commitment amplifies the randomness instead of compounding correct judgment. Branching-factor (14 vs. 10, worse) and particle-count (80 vs. 40, no clear gain) sweeps didn't move the needle either.

**`maxRounds` (cap decisions at 5)**: only genuine ≥2-way decisions (oracle consulted) count against it — unambiguous auto-descends are free. Once the budget is used up but the tree is still ambiguous, the session silently follows the model's own top-supported child rather than stalling.

**Success metric matches `GridFeedbackSearch`'s convention, not `evaluate.py`'s**: an acceptance set (target's own top-10 nearest neighbors in the whitened space) rather than the single exact font. A second, more direct metric is also tracked: whether the search's own final narrowed group (now ~5-10 fonts) contains an acceptance-set font at all, independent of any re-ranking against the full corpus.

**Empirical results** (120 held-out queries, 40 particles/round, `branchingFactor=10`, `treeDepth=5`, `minClusterSize=2`, `persistFor=4`, `maxRounds=5`, 50/1000 steps — full sweep charted at https://claude.ai/code/artifact/37cece46-ad65-45ec-aab2-f18008541e46, raw numbers in `experiments/diffusion-searches/branching_results_final.json`): single-shot baseline (no branching) recall@10 = 0.033, recall@100 = 0.20. Branching + oracle (`hard`) at noiseProb=0: recall@10 = 0.20 (**~6x baseline**), recall@100 = 0.45 (~2.25x baseline). Degrades cleanly and monotonically with noiseProb — recall@10 0.20→0.05 and recall@100 0.45→0.16 from noiseProb 0→1, converging on the no-branching baseline exactly at noiseProb=1 (oracle = coin flip), the sanity check a working noise model should pass. **Remaining gap to the tree's own ~97% omniscient ceiling is now squarely the diffusion model's own per-level accuracy** (~47% top-1 / ~87% top-3 at the root, presumably lower deeper in the tree) — the corpus, the metric, the search protocol's addressable resolution, and (per finding 5) recovery-from-error mechanisms were all real, testable hypotheses, now either fixed or empirically rejected as the lever; closing more of the remaining gap without retraining the pretrained ViT backbone or the finetuned contrastive embedder (out of scope) means training the small diffusion MLP itself further or differently. **Tried, and it didn't help — a real, tested result, not a remaining open question:** `diffusion.ResidualBlock` now supports `conditioning="film"` (Perez et al. 2018 — text/timestep modulate the hidden state's scale/shift instead of being concatenated alongside it) as an alternative to the original `"concat"`, selectable via `train.py --conditioning`/`--checkpointDir`. Trained a `checkpoints/diffusion_film` run: identical hyperparameters and epoch count (60) as the deployed `checkpoints/diffusion` checkpoint, only the conditioning mechanism changed. Two independent signals both point the same way: (1) training loss converged HIGHER, not lower (0.106 vs. the original's 0.063 final loss, same MSE-on-noise objective) — FiLM's extra parameters (a 2x-wider projection per block) evidently didn't pay for themselves in the same 60-epoch budget; (2) the full branching+oracle pipeline, same 60 held-out queries, same noiseProb=0: recall@10 = 0.117 (FiLM) vs. 0.20 (concat) — worse, not better; recall@100 was roughly comparable (0.40 vs. 0.42). A single-shot exact-match check (`evaluate.py`, n=60) was too close to the noise floor for both (concat 0/60, FiLM 1/60) to be informative on its own. Read together: this specific FiLM implementation, at this training budget, is a regression, not an improvement — worth remembering before re-suggesting "try FiLM conditioning" as if it were still untested. If conditioning strength is revisited, the more promising next step per this result is probably training FiLM longer (its extra parameters may need more than 60 epochs to earn their keep) before concluding the mechanism itself doesn't help, or trying cross-attention instead (a bigger change, not yet attempted).

### Supervised navigation classifier — supersedes diffusion sampling for decision-making, target hit

**GRPO fine-tuning of the diffusion sampler was tried first and is now deprioritized.** `experiments/diffusion-searches/grpo_finetune.py` implements decision-aware GRPO (conditions on `[text; currentNode.centroid]`, widens `textProjection` with zero-init columns to warm-start from the supervised base, DDPO-style closed-form Gaussian log-probs per reverse-diffusion step, `--beamWidth` independent noisy-oracle replicates pooled per GRPO group). A graded terminal reward (rank<5→1.0, rank<10→0.5, rank<100→0.1, else −1.0; plain exact-match reward gave literally zero training signal, and per-level correct-child reward was rejected as reward-hacking-prone — it lets the model spread particles across children rather than genuinely improving belief) was the working version, but measured recall@10=0.10–0.25 at n=60–300 — worse than doing nothing extra, and never beat the baseline branching search convincingly at a reliable sample size. Known unfixed gap: no gradient clipping (loss swung as high as ±85 over 500 iterations). Not resumed once the classifier below started outperforming it by a wide margin for far less compute.

**The actual fix: stop using diffusion sampling for navigation decisions at all.** Every prior approach picked a tree child indirectly — generate a sample via reverse diffusion, then nearest-centroid-assign it to a child. That's a slow, noisy generative process standing in for what is really a direct classification problem: given `(text, currentNode)`, which child contains the target? `experiments/diffusion-searches/train_navigation_classifier.py` trains a small MLP scoring each child individually via `[text; nodeCentroid; childCentroid]` (handles any branching factor, no fixed-size softmax head), supervised with cross-entropy against the *known* true child along each target's real tree path — ground-truth examples are pure tree lookup, free to generate at any scale, no model or diffusion calls needed at all. `experiments/diffusion-searches/evaluate_classifier_branching.py` runs the same tree/oracle/decision-budget protocol as the diffusion branching search, but scores children with this classifier instead of nearest-centroid-on-a-generated-sample; at the final leaf (no generated point exists to rank against) it ranks the leaf's real members by distance to the leaf centroid, a crude proxy — but recall@10 is already ~96% of recall@100 in practice, so this proxy is not costing much.

Scaling the classifier's training data/epochs/capacity gave large, monotonic, verified gains that eventually flattened: v1 (60k examples/15ep/hidden128) pooled top1/top3 = 0.412/0.782; v2 (300k/30ep/hidden256) = 0.459/0.824; v3 (600k/50ep/hidden384) = 0.523/0.854; v4 (771k/60ep/hidden384, ~all available data) = 0.543/0.861 — a much smaller jump than v2→v3, confirming the scaling curve had flattened by v4. **Auto-descending on the classifier's own softmax confidence measured strictly worse than always spending the full oracle-consultation budget**, despite looking harmless in isolation: a threshold sweep on v2 (`--autoThreshold` 0.6→recall@10=0.3633, 0.85→0.4667, disabled/1.01→0.4767, all n=300) was monotonic — the model's confidence doesn't track correctness closely enough to be trusted over an oracle that's actually available within the 5-decision budget. `--autoThreshold` now defaults to 1.01 (auto-descend off) in `evaluate_classifier_branching.py`.

**Depth 1 was a persistent weak point across every scale (v1–v4, top1 stuck ~0.38–0.45, top3 ~0.71–0.76) that generic scaling didn't fix** — not a data-imbalance artifact, since depths are already roughly balanced in raw example count (~150k each at full scale). `--depthWeights` (per-depth cross-entropy loss weighting, e.g. `1,3,1,1,1`) was added to test this directly. At v2 scale it worked cleanly: depth-1 top1/top3 improved (0.380→0.399 / 0.711→0.733) at a small cost to depths 3–4, pooled accuracy roughly flat (0.459→0.454), but full-session recall@10 improved 0.4767→0.5067 (n=300) — a real gain from a flat/lower *average*, because recall@10 is bottlenecked by the weakest link compounding across 5 decisions, not the per-level mean. **The same depth-weighting did NOT transfer to v4 scale** (v5 = v4 config + `depthWeights=1,3,1,1,1`): depth-1 still improved (0.424→0.449/0.755→0.766) at the same small cost elsewhere, but this time recall@10 came out *worse* than unweighted v4 at both noiseProb=0 (0.6410 vs. 0.6620, n=1000) and noiseProb=0.1 (0.4233 vs. 0.4767, n=300) — a genuine negative result, not a fluke (checked at both noise levels). Read together: depth-weighting's benefit shrinks or reverses once baseline accuracy is already higher, because the tradeoff cost against depths 3–4 (already strong, high-leverage contributors at that point) starts to outweigh the depth-1 gain. A milder weight (v6 = v4 config + `depthWeights=1,1.5,1,1,1`) confirmed this rather than escaping it: best pooled accuracy of any checkpoint (top1=0.5451) and the smallest per-depth tradeoff of the three weightings, but recall@10 landed within noise of unweighted v4 either way (0.6440 vs. 0.6620 at noiseProb=0 n=1000; 0.4800 vs. 0.4767 at noiseProb=0.1 n=300) — **depth-weighting is a genuinely exhausted lever at this scale, not just a mistuned one.** v4 (unweighted) is the reported-best checkpoint: equally good, and simpler.

**Beam search over the classifier's decisions is a real, unambiguous win, added after the user directly pushed back on settling for the perfect-oracle result.** `evaluate_classifier_branching_beam.py`: the oracle still only ever sees/clicks ≤3 options per round exactly as before, but non-chosen candidates are no longer discarded — they're kept alive as classifier-weighted "hedge" branches, auto-advanced each round via the classifier's own top-1 choice, and at the end recall@k is checked against the union of all live branches' leaf members (primary branch first, then hedges by descending weight). This is a materially different mechanism from the earlier diffusion-investigation "hedge"/`reserveX` idea (classifier-confidence-weighted pooling vs. uniform branch pooling) and was sanity-checked correct (`beamWidth=1` exactly reproduces the hard-commit baseline) before trusting wider results. Measured (nav_classifier_v4): noiseProb=0.0 (n=1000) hard-commit 0.6620 → beamWidth=3 0.6640; noiseProb=0.1 (n=300) 0.4767 → beamWidth=2 0.5100 → beamWidth=3 0.5200; noiseProb=0.2 (n=300) 0.3667 → beamWidth=3 0.4300 — a real win at every noise level, growing with both beam width and noise level, with no downside at noiseProb=0. `--hedgeBranchWidth` (each hedge branch spawns its own top-N children per round instead of collapsing to top-1) was added to test whether recall@10 specifically could capture more of the gains a wider beam brings to recall@100 (a `beamWidth=5` sweep showed recall@100 jumping 0.5367→0.6033 at noiseProb=0.1 while recall@10 barely moved, 0.5200→0.5233 — wider beams recover many sessions from total failure but the recovered candidates rank too low in the pooled ordering to reach the top-10 a real user would see).

**Root cause of the remaining recall@100 ceiling (~1/3 of sessions get zero acceptance-set hits regardless of ranking depth), found via direct diagnosis, not assumption:** `diagnose_top3_miss.py` walks each query's TRUE tree path and checks whether the true child is inside the classifier's own top-3 at every level — a miss at ANY level is structurally unrecoverable by hard-commit OR beam search, since hedge branches are only ever drawn from that same top-3. Measured (v4, n=1000): 36.2% of sessions miss at some level, closely matching the observed ceiling, and the misses are heavily concentrated at depths 0 and 1 (18.1%/14.4% miss rate, 84% of all first-misses combined) — depths 2-4 are far more reliable (1.3-4.8%). Tried fixing this via loss-weighting depth 0 specifically (as well as combined with depth 1) at v2 scale, since prior depth-weighting work only ever touched depth 1: **depth-0 accuracy proved genuinely immovable by training emphasis** — even an aggressive weight=4 (depth-0-only) barely nudged top3 (0.763→0.769), and a combined depth0+depth1 weighting (`2,1.5,1,1,1`) left the matched-scale top-3-miss rate unchanged within noise (55.4%→56.5%, unweighted vs. weighted v2). This closes the depth-weighting investigation for good, at every value tried across every scale.

**Why depth 0/1 specifically, when depth 4 also has branching=15 but a LOW miss rate:** the risk isn't branching factor in the abstract, it's branching factor paired with a genuinely hard (broad, semantically-confusable) decision. Near-leaf groups are tight/near-duplicate (consistent with this investigation's own ~0.96 nearest-neighbor corpus-density finding), so even a hard 15-way choice is easy once you're deep in the tree — it's specifically the shallow, broad-category splits that are both high-branching AND hard. There's also a sharp arithmetic reason smaller branching helps independent of any accuracy gain: showing top-3 of 15 covers only 20% of possible answers; top-3 of a 4-way split covers 75% — a top-3 miss becomes structurally rarer regardless of whether the classifier gets any better. Since depth-0/1 accuracy can't be trained higher, `build_deeper_tree.py` restructures the tree instead: replaces the two branching-15 shallow levels with three branching-4 levels (`tree_variant_4_4_4_5_5_15.pkl`, 6 levels total, `[4,4,4,5,5,15]`), leaving the rest of the schedule alone since those levels aren't the problem. This also finally gives the existing interleaved auto-descend logic in `evaluate_classifier_branching.py` (already fires whenever confidence clears `--autoThreshold` at ANY depth, not just past the round budget — the reason it hasn't helped before is that `maxDepth==maxRounds==5` left no slack to spend) somewhere to actually save real oracle-asks, since the tree is now deeper than the 5-ask budget. Not yet evaluated — results pending.

**A new "leaf-success rate" metric (does the search land in the leaf actually containing the true target font, not just an acceptance-set neighbor) was added per the user's request, motivated by the tree's leaf-size outliers (max 150, a k-means degenerate-cluster artifact) — but only after validating it actually measures something meaningful, not assumed.** First attempt at validation (`diagnose_leaf_similarity.py`) measured "fraction of leaf-mates within a member's own top-10 nearest neighbors" and found large leaves scored much lower (0.11 for 51+ vs. 0.70 for 2-5) — **this was WRONG, caught by the user directly**: a fixed top-10 neighbor set against a leaf of size N has a hidden ceiling of `min(1, 10/(N-1))` regardless of actual similarity (10/99≈0.101, almost exactly the flawed 0.11 result) — large leaves were being penalized by their own size, not measured for coherence. Corrected version measures direct pairwise cosine similarity within each leaf instead (no size-dependent ceiling), against same-size random-group baselines: 2-5→0.83, 6-20→0.78, 21-50→0.69, **51+→0.74** (all vs. a ~0.00-0.01 random baseline) — the large leaves are NOT a junk drawer; if anything they're slightly tighter than the 21-50 bucket, consistent with the k-means warning that prompted them (near-duplicate points too similar to separate, not too dissimilar to cluster). Leaf-success is validated as meaningful across every leaf size, not just small ones. `evaluate_classifier_branching.py`/`evaluate_classifier_branching_beam.py` report it stratified by leaf size regardless, since that's cheap and keeps the metric auditable.

**Open, flagged methodological question raised by the user, not yet resolved: is Euclidean distance the wrong metric for this whole pipeline?** These embeddings are designed to be operated on with cosine similarity, but `HierarchicalClusterIndex.fit` (sklearn KMeans/MiniBatchKMeans, no cosine option), `corpus.nearest` (the acceptance-set definition used by every recall@k number in this investigation), `rankInLeaf`, and `oracleChoiceAmongChildren` all use Euclidean distance in the whitened space instead. This matters because `‖u−v‖² = |u|² + |v|² − 2|u||v|cos(θ)` — Euclidean and cosine rank identically only when all vectors share a norm, and this corpus's don't: `diagnose_metric_choice.py` measured whitened-space norms at mean=8.36 but ranging 1.94–14.09 (a ~7.3x spread, actually WORSE than the raw embeddings' documented 0.70–1.00 spread — whitening amplified rather than fixed this, consistent with the still-unconfirmed "outlier-PC whitening pathology" hypothesized earlier for the historical loss discrepancy). Measured impact: Euclidean-nearest-10 vs. cosine-nearest-10 top-k overlap averages 0.85/0.90 (mean/median) across a 500-query sample — most queries route similarly under either metric — but has a real tail down to 0.0 (complete disagreement), correlated with a font's own norm (r=0.27), i.e. exactly the outlier-norm fonts the theory predicts would be most affected. Practical read, not yet verified further: average-case recall@10 numbers are probably not grossly invalidated by this, but it's a plausible contributor to the catastrophic-failure tail (the ~33% recall@100 ceiling / top-3-miss rate above) — if the acceptance-set ground truth itself uses the wrong notion of similarity for outlier-norm fonts, no navigation algorithm could succeed on those by construction. Switching the whole pipeline to cosine (spherical k-means for the tree, cosine-based acceptance sets, full re-evaluation of every checkpoint) is a substantial re-engineering effort, not yet started or committed to — flagged here for a decision, not fixed unilaterally.

**Best validated checkpoint: v4 (unweighted, 771k examples/60ep/hidden384/`--autoThreshold` disabled).** Full branching+oracle rollout eval (`evaluate_classifier_branching.py`, `--maxOptions 3`, `--maxRounds 5`, matching the hard constraints of ≤5 decisions/session and ≤3 options/decision — constraints held throughout at median=5.0 decisions, max=3 options): **recall@10 = 0.6620 at n=1000 (noiseProb=0, independently verified against a separate n=300/seed=1234 run at 0.5600)** — comfortably clears the 0.50 target that was the standing goal for this investigation, and is by far the best result of the whole branching-search effort (prior best: diffusion+nearest-centroid branching at recall@10=0.20, n=120, noiseProb=0; GRPO-finetuned diffusion at recall@10=0.10–0.25). **Caveat, real and worth keeping in view: this holds only under a perfect oracle.** Under a realistic noisy oracle (same noise model as the diffusion branching investigation — a uniform-random wrong pick among shown candidates with probability `noiseProb`), recall@10 degrades fast: 0.4767 at noiseProb=0.1, 0.3667 at noiseProb=0.2 (both n=300, v4). The navigation-accuracy problem this investigation set out to solve is genuinely solved; oracle-noise robustness is a separate, still-open problem with real headroom (the diffusion branching investigation's own `hedge`/recoverability work above found real but limited gains from a different mechanism — not yet re-tried against this classifier's setting).

### Suggested next steps (not yet decided/started), navigation classifier

Both tested scaling levers (raw data/capacity, per-depth loss weighting) have shown diminishing-to-negative returns by v4/v5 — likely near this approach's practical ceiling without a different lever. (a) Noise-robustness is the most valuable unexplored direction now that perfect-oracle recall is solved: blending the classifier's own top-1 belief with the (possibly wrong) oracle's answer, rather than committing 100% to whatever the oracle clicks, is untested for this classifier setting specifically (a similar "recoverability from a wrong decision" idea for the diffusion approach mostly didn't pay off — see finding 5 above — but the mechanism here is materially different, so don't assume the same verdict without testing).
